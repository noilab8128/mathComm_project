# 생성 문제 검증, 어디서 어떻게 할까

- 작성: 2026-10-14 · 논의용
- 대상: Math Quest 사다리 문제 (공개 145문제와 앞으로 만들 문제)
- 근거: OPERATING_POLICY, LADDER_RULES_v2, WORKLOG 10-04~10-11, review_v0.3.pdf, verify 스크립트 6개

문제는 공식 오픈 뒤에도 배치 단위로 계속 만들어집니다. 두 사람이 따로 일해도 검증은 저절로 돌아가야 하고, 사람은 마지막 승인만 해야 합니다.
이 문서는 검증 절차와 방법, 그것을 만들기 위해 필요한 것, 함께 정해야 할 것을 정리합니다.

---

## 1. 요약

**검증은 GitHub Actions에서 자동으로 실행하고, 결과는 Supabase에 쌓고, admin 페이지에서 사람이 승인합니다. 승인된 문제만 학생에게 보입니다.**

| 위치 | 역할 | 하는 일 |
|---|---|---|
| GitHub Actions | 검증 실행 | 문제 파일이 push되면 자동 실행 · Python 검사(형식, 검증 스크립트, 정답 대조) · Claude를 headless로 실행하는 AI 검사 · 통과하면 숨김 상태로 import |
| Supabase | 결과 보관 | 문제별, 단계별 검증 결과와 근거 · 어느 커밋, 어느 실행에서 나온 결과인지 · 공개 후 오답 분포 집계 |
| admin (`src/app/admin/problems`) | 사람 승인 | 검토 대기열에서 승인 또는 반려 · "증명 의존" 문제는 증명을 읽고 판단 · 다시 검증 버튼 |

웹 서버(Netlify)에서는 검증을 돌리지 않습니다.

- Netlify Functions는 JavaScript, TypeScript, Go만 지원해서 Python 스크립트를 실행할 수 없습니다.
- 무거운 계산이나 AI가 만든 코드를 학생 요청을 처리하는 서버에서 실행하면 안 됩니다.
- Supabase Edge Functions도 TypeScript 전용입니다.

## 2. 절차

### 2.1 초안부터 공개까지

| 순서 | 실행 위치 | 단계 | 내용 |
|---|---|---|---|
| 1 | 문제 담당 | Markdown과 verify 스크립트 push | PR 하나에 배치 하나 |
| 2 | Actions · Python | L0 형식, L1 스크립트, 정답 대조 | 실패하면 여기서 멈춤 |
| 3 | Actions · Claude | L2–L6 AI 검증 | 독립 재계산, 풀이, 애매함, 규칙, 유사도 |
| 4 | Actions → Supabase | 숨김 상태로 import, 결과 저장 | 학생에게는 아직 안 보임 |
| 5 | admin | **L7 사람 승인** | 승인하면 공개, 반려하면 사유 기록 |
| 6 | 밤 · SQL | L8 공개 후 관찰 | 이상한 문제를 대기열로 되돌림 |

### 2.2 트리거

- **문제 파일 PR/push** (`olympiad/ladders/**`): 주 트리거입니다. 문제 담당자는 지금처럼 markdown을 쓰고 push만 합니다.
- **매일 밤**: "대기" 상태 문제를 다시 확인하고 L8을 집계합니다.
- **admin의 다시 검증 버튼**: GitHub API(`workflow_dispatch`)로 같은 workflow를 실행합니다.

### 2.3 AI 검사의 자동 실행

- Claude Code 스킬은 세션 안에서만 돌기 때문에, Actions에서 Claude Code를 headless로 실행합니다(`claude -p` 또는 공식 GitHub Action).
- 스킬과 프롬프트는 저장소의 `.claude/skills/`에 둡니다. 로컬에서 수동으로 돌릴 때와 CI에서 같은 스킬을 씁니다.
- AI가 만든 코드는 실행할 때마다 새로 뜨는 Actions 가상 머신 안에서만 실행됩니다.

## 3. 방법: 검증 단계

- **차단**: 실패하면 import를 멈춥니다.
- **경고**: 기록만 하고, L7에서 사람이 판단합니다.
- 숫자 검사(L1, L2)는 답이 맞는지만 알려 줍니다. 좋은 문제인지는 L4, L5, L8이 봅니다.

| 단계 | 내용 | 실행 | 처리 | 구분 |
|---|---|---|---|---|
| L0 | **형식 점검.** 정답이 `/api/check-answer`로 해석되는지, 힌트에 정답이 없는지(`import_guides_hints.py`의 검사 재사용), "use your answer from step 2" 같은 표현, 난이도 라벨, subdomain, Theory 카드, 같은 사다리 안의 중복 정답 | Python | 차단 | 신규 제안 |
| L1 | **작성자 검증 스크립트** 실행, 그리고 markdown 정답과 대조 | Python | 차단 | 기존 규칙 |
| L2 | **독립 재계산.** 문제 문장만 받은 별도 AI가 자기 코드를 짜서 답을 비교합니다. 작성자가 문제를 잘못 읽으면 정답과 스크립트가 같은 방향으로 틀리는데, 이것을 잡습니다. 끝까지 셀 수 없는 Challenge는 작은 경우만 확인하고 "증명 의존"으로 표시합니다 | Claude | 차단 | 신규 제안 |
| L3 | **AI 독립 풀이.** 정답 없이 여러 번 풀어 일치도를 보고, 애매한 곳을 보고받습니다. AIME 수준은 AI도 자주 틀리므로 신호로만 씁니다 | Claude | 경고 | 기존 규칙 |
| L4 | **애매함 탐지.** 가능한 다른 해석(0 포함 여부, 순서 유무 등)마다 답을 계산해서 답이 갈리면 표시 | Claude | 경고 | 신규 제안 |
| L5 | **규칙 평가.** LADDER_RULES_v2 §9: 한 단계에 한 수, 숫자가 그 수를 시험하는지, 손으로 풀 수 있는지(5.6), Challenge가 추측으로 풀리지 않는지(4.3) | Claude | 경고 | 신규 제안 |
| L6 | **원본 유사도와 저작권.** 아이디어 카드(Supabase에서 서비스 키로 읽음)와 비교, 변형 포인트 웹 검색 (규칙 2.4) | Claude | 경고 | 기존 규칙 |
| L7 | **사람 승인.** L0–L6 결과와 "증명 의존" 표시를 보고 승인 또는 반려 | admin | 공개 조건 | 기존 규칙 |
| L8 | **공개 후 관찰.** 한 오답에 제출이 몰림(정답 오류나 애매함의 신호), 정답률, 그만두는 단계, 신고 버튼 | Supabase SQL | 대기열로 되돌림 | 신규 제안 |

## 4. 현재 상태

### 4.1 기존 검증 스크립트 점검

대상은 `pilot_v2/verify_pilot_a2.py`, `v2/verify_v2_batch1~4.py`, `v2/verify_v2_older.py`입니다.
코드를 읽고 실행하고, markdown 정답 108개와 대조했습니다. 계산이 가능한 Challenge는 다른 방법으로 다시 풀었습니다.

| 결과 | 내용 |
|---|---|
| **220 / 220** | 모든 검사 통과. WORKLOG에 적힌 수(28, 45, 40, 37, 45, 25)와 같고, 전체 실행은 15초 안팎입니다. |
| **108 / 108** | markdown 정답과 스크립트 기대값 일치. 99개는 정답 값을 직접 확인하고, 9개는 목록 등으로 간접 확인합니다. |
| **11 / 11** | Challenge 독립 재계산 일치. 대상은 P2, P8, P9, P13, P15, P16, P17, P19, P21, 그리고 P18(n = 7, 8로 범위 확장)입니다. 예: P17은 GF(2) 계수, P19는 최단 경로, P21은 8개 추를 직접 셈. |

**지금 공개된 답은 맞습니다. 다만 이 스크립트를 자동 검증의 기반으로 쓰려면 다음을 고쳐야 합니다.**

| 심각도 | 문제 | 영향 | 수정 |
|---|---|---|---|
| 자동화 차단 | **검사가 실패해도 종료 코드가 0.** 마지막에 "x/y checks pass"만 출력합니다. | CI가 실패를 통과로 처리합니다. | 실패가 있으면 `sys.exit(1)` |
| 자동화 차단 | **스크립트가 markdown을 읽지 않음.** 기대값을 코드에 직접 적고, import 스크립트도 verify를 실행하지 않습니다. | 검증 뒤에 markdown 정답만 바뀌어도 그대로 import됩니다. | 정답을 `parse()`로 읽어 비교하고, 단계마다 검사가 있는지 확인 |
| 검사가 약함 | **P7 Challenge:** "128줄이면 8개 보장"을 `(128).bit_length() == 8`로 확인합니다. 항상 참인 식입니다. | 128 쪽 하한은 증명과 n ≤ 8 전수 검사에만 기댑니다. | 검사 이름을 실제 내용에 맞추고 "증명 의존"으로 표시 |
| 검사가 약함 | **P10 Challenge:** `max(1, N + j − N)`는 j와 같아서 집합 크기가 저절로 2027이 됩니다. | 2027이라는 답 자체를 확인하지 않습니다. | 위와 같음 |
| 설명과 다름 | **P10 풀이:** "m, n이 2500까지 모두 확인"이라고 적었지만, 실제로는 1500까지와 일부 표본만 확인합니다. | 학생에게 보이는 풀이 문구가 실제보다 강합니다. | 문구를 실제 범위에 맞춤 |
| 정답 미확인 | **P2 Step 2, P18 Step 2:** 값 목록이나 경로만 확인하고 정답(6, 4) 자체는 확인하지 않습니다. | 정답 칸 오타를 놓칩니다. | 정답 값을 직접 확인 |
| 한계 근접 | **P15 Challenge:** 8쌍(예: 7과 30)은 승수 s가 10,800 근처에서야 나오는데, 탐색 한도가 20,000입니다. | 지금은 맞습니다. 더 큰 수를 쓰는 새 문제에서는 한도에 걸려 실패할 수 있습니다. | 한도를 문제 크기에 맞추고 찾은 s를 기록 |
| 사람 확인 필요 | **증명에 기대는 Challenge:** P3(n ≤ 7만 전수), P7(n ≤ 8), P10, P18(n ≤ 8), P20(하한은 AM–GM 증명) | 작은 경우가 맞아도 규칙이 깨질 수 있습니다. | "증명 의존"으로 표시하고 L7에서 증명 확인 |
| 형식 | **파일마다 형식이 다름.** 파일럿은 검사 이름에 사다리 번호가 없고(`"Step 1: …"`), `check()`를 파일마다 새로 정의합니다. | 결과를 문제와 자동으로 연결할 수 없습니다. | 공용 모듈 하나와 이름 규칙(`"P1 Step 1"`) |

## 5. 검증과 함께 알아야 할 것

### Challenge가 승인 대기열에 나오지 않음

- import 스크립트는 단계에 `is_generated = true`, Challenge에 `false`를 넣습니다(`import_ladders_v2.py` 137행).
- admin의 "Pending AI Review" 필터와 승인 버튼은 `is_generated = true`인 문제에만 나옵니다.
- 그래서 **Challenge 28개는 지금 승인 화면에 나타나지 않습니다.** Challenge도 생성한 문제이므로 플래그 의미를 다시 정해야 합니다.

### 숨김만으로는 정답이 보호되지 않음

`solutions` 테이블은 공개 키로 읽을 수 있습니다(WORKLOG §10). 승인 전 문제를 화면에서 숨겨도 정답은 그대로 읽힙니다.
숨김 처리와 `solutions` 읽기 정책 수정을 같이 해야 합니다.

### 공개 저장소와 Actions 로그

- 공개 저장소에서는 Actions 로그를 누구나 봅니다. 검증 로그에는 정답과 출처가 찍힙니다.
- 이미 커밋된 `LADDERS_v2_batch*.md`와 v0.x 초안에도 정답과 `Idea card: SL…` 줄이 들어 있습니다. 출처를 내부용으로 둔다는 OPERATING_POLICY 2.4와 맞지 않습니다.

### 검증 범위

- **먼저:** 이미 공개된 145문제. v2 P1–P21(108문제)과 v0.1 사다리 7개(37문제)가 모두 `is_reviewed = false` 상태로 학생에게 보이고 있습니다.
- **v0.1:** 단계가 풀이 경로에서 벗어난 곳과, 1단계가 v2 기준보다 낮은 문제가 있습니다(WORKLOG §11-3). 검증 결과로 교체 여부를 정할 수 있습니다.
- **파이프라인 밖:** 증명 문제(16 + 21)는 숫자 답이 없어 L1–L4가 맞지 않습니다. 사람이 읽는 별도 목록으로 관리합니다. Theory 카드 링크도 주기적으로 확인합니다.
- **나중에:** 초안 G/H(v0.2), I–AB(v0.3)는 v2로 다시 만들 때 같은 절차를 거칩니다.

### 채점기와의 관계

풀이 제출 채점(`/api/grade-solution`)은 저장된 정답을 쓰지 않고 AI가 직접 풀어 판단합니다. 그래서 어려운 Challenge는 잘못 채점될 수 있습니다(OPERATING_POLICY 3).
검증을 통과한 정답을 채점에도 쓰게 하면 이 한계가 줄어듭니다.

| GitHub Secrets | Claude API 키, Supabase URL과 서비스 키. 지금은 로컬 `olympiad/.env`에만 있음 | 함께 |

| 승인 전 숨김 | 사이트 문제 조회에서 미승인 문제 제외, `solutions` 읽기 정책 수정, Challenge 플래그 정리 | 앱 담당 |
| admin 대기열 | 기존 "Pending AI Review"와 승인 버튼을 확장: 단계별 결과, 증명 의존 표시, 반려 사유, 다시 검증 버튼 | 앱 담당 |
| L8 집계 | 제출 기록에서 오답 분포, 정답률, 그만두는 단계를 매일 계산 | 앱 담당 |

### 결과 테이블 초안

```
problem_verifications
  id            uuid
  problem_id    → problems.id
  layer         'L0' … 'L8'
  status        'pass' | 'warn' | 'fail'
  strength      'direct' | 'two_methods' | 'small_cases_plus_proof'   -- 증명 의존 표시
  details       jsonb      -- 기대값/계산값, 다른 해석, 평가 근거
  source_file   text       -- 예: ladders/v2/LADDERS_v2_batch1.md
  commit_sha    text
  run_url       text       -- GitHub Actions 실행 링크
  model         text       -- AI 단계일 때
  reviewer_id   → users.id -- L7일 때
  created_at    timestamptz
```

다른 내부 테이블(`idea_cards`, `ladder_guides`)처럼 RLS를 켜고 읽기 정책 없이 서비스 키와 관리자 API로만 접근합니다.
