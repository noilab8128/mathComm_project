## 0. 목표

> Supabase DB에 등록된 모든 문제를 **자동으로 검증**하고, **여러 리뷰어가 검토·코멘트**한 기록을 남긴다.
> 정한 기준만큼 승인을 받은 문제만 학생에게 보인다.

## 1. 이전 계획과 달라진 점

| 항목 | 이전 계획 (10-14) | 이번 계획 |
|---|---|---|
| 검증 대상 | `olympiad/ladders/`의 markdown과 검증 스크립트 | **Supabase DB에 저장된 문제** (`problems`, `solutions`, `problem_hierarchies`) |
| 검증 시작 시점 | 문제 파일을 push할 때 | DB의 문제가 **새로 생기거나 바뀌었을 때** (매일 밤 자동 + 관리자 화면 버튼) |
| 사람 검토 | 관리자 1명이 승인 | **리뷰어 여러 명.** 같은 문제를 여러 사람이, 같은 사람이 여러 번 리뷰 가능 |
| 기록 | 실행 기록 | **문제별 검증 상태 + 리뷰 기록 + 리뷰어 코멘트** |
| markdown·검증 스크립트 | 필수 | 참고 자료 (있으면 DB 정답과 대조) |
| `review_v0.3.pdf` | 예시로 사용 | 검증 대상 아님 (참고용 예시였음) |

DB를 기준으로 하면 관리자 화면에서 고친 문제, 사다리가 아닌 문제, 예전 문제까지 **학생에게 실제로 보이는 그대로** 검증할 수 있습니다.
markdown 원본과 DB가 어긋난 경우도 찾을 수 있습니다.

## 2. 전체 흐름

```
문제가 DB에 들어감 (import, 관리자 화면, 문구 수정)
   ↓ 자동 (매일 밤 / "다시 검증" 버튼)
자동 검증 L0–L6 → 문제별 결과 저장
   ↓
리뷰어 여러 명이 결과를 보고 리뷰 (승인 / 수정 요청 / 반려 / 의견) + 코멘트
   ↓ 승인 기준을 채우면
학생에게 공개 (problems.is_reviewed = true)
   ↓ 이후 문제 내용이 바뀌면
"재검증 필요" → 다시 자동 검증 → 다시 리뷰
   ↓ 매일 밤
L8 공개 후 관찰: 오답이 몰리는 문제를 다시 리뷰 대기로
```

## 3. 리뷰 (여러 리뷰어, 기록, 코멘트)

### 3.1 리뷰 규칙

1. **리뷰어는 여러 명**일 수 있습니다. 누가 리뷰어인지는 8장 결정 5로 정합니다.
2. **같은 문제를 여러 리뷰어가** 각각 리뷰합니다. 앞사람이 승인했어도 다른 리뷰어가 다시 리뷰할 수 있습니다.
3. **같은 리뷰어가 여러 번** 리뷰할 수 있습니다. 상태를 정할 때는 **그 리뷰어의 마지막 판정**만 셉니다. 이전 리뷰는 기록에 그대로 남습니다.
4. 리뷰 기록은 **지우거나 고치지 않습니다.** 잘못 적었으면 새 리뷰로 바로잡습니다 (감사 기록).

### 3.2 리뷰 종류

| 종류 | 뜻 | 코멘트 |
|---|---|---|
| **승인** | 이대로 공개해도 됨 | 선택 |
| **수정 요청** | 고친 뒤 다시 보자 (오탈자, 애매한 문장, 난이도 라벨 등) | **필수** |
| **반려** | 이 문제는 쓰지 말자 (정답 오류, 원본과 너무 비슷함 등) | **필수** |
| **의견** | 판정 없이 코멘트만 남김 (질문, 참고 사항) | 필수 |
| **판정 철회** | 내 현재 판정(승인·수정 요청·반려)을 없애고 "판정 없음"으로 되돌림. 철회로 승인이 풀리면 다시 숨김 (2026-11-18 추가) | 필수 |

자동 검증이 "실패"인 문제를 승인하려면 **코멘트가 필수**입니다 (예: "자동 검증 오탐, 손으로 확인함").

### 3.3 문제 상태를 정하는 방법

**현재 문제 내용**에 대한 리뷰만 셉니다. 각 리뷰어의 마지막 판정을 모아 아래 순서로 정합니다.

| 순서 | 조건 | 상태 |
|---|---|---|
| 1 | 반려가 하나라도 있음 | **반려** |
| 2 | 수정 요청이 하나라도 있음 | **수정 요청** |
| 3 | 승인 수 ≥ 필요 승인 수 | **승인** → 학생에게 공개 |
| 4 | 그 밖 | **리뷰 대기** (예: "승인 1/2") |

- 필요 승인 수는 기본값을 두고 문제마다 바꿀 수 있게 합니다 (8장 결정 4). 예: 단계 문제 1명, Challenge 2명
- 수정 요청이나 반려를 한 리뷰어가 나중에 승인하면, 그 리뷰어의 마지막 판정이 승인이 되어 상태가 다시 계산됩니다.

### 3.4 문제 내용이 바뀌면

- 문제 제목, 본문, 난이도·라벨, 풀이(정답)를 합쳐 **내용 지문(hash)**을 만들어, 리뷰할 때마다 함께 저장합니다.
- 내용이 바뀌면 이전 리뷰는 **기록에 남지만 상태 계산에서는 빠집니다.** 문제는 "재검증 필요"가 되고, 자동 검증을 다시 거친 뒤 다시 리뷰합니다.
- 관리자 화면 수정, import, `--update-text` 중 무엇으로 바뀌었든 같은 방식으로 잡힙니다.
- 재검증 중에 학생에게 계속 보일지는 8장 결정 3으로 정합니다.

## 4. 데이터 구조

`problems` 테이블 구조는 바꾸지 않습니다 (import 스크립트에 영향이 없도록). 기존 열은 이렇게 씁니다.
- `is_reviewed`: 공개 여부. 3.3의 상태가 "승인"일 때만 `true`
- `reviewer_id`: 마지막으로 승인한 리뷰어 (호환용)

**새 테이블 3개.** 모두 RLS를 켜고 공개 정책을 두지 않습니다. 관리자·리뷰어 API(서버, 서비스 키)로만 읽고 씁니다.

```
problem_verification_status      -- 문제당 한 줄: 현재 상태
  problem_id          → problems.id (기본 키)
  content_hash        text        -- 현재 내용 지문
  auto_status         text        -- 자동 검증: unverified | passed | warning | failed
  auto_summary        jsonb       -- 단계별 결과 요약 {L0: pass, L2: fail, ...}
  review_status       text        -- pending | approved | changes_requested | rejected | needs_recheck
  required_approvals  int         -- 필요 승인 수 (기본값은 결정 4)
  approvals           int         -- 현재 내용에 대한 승인 수
  last_checked_at     timestamptz
  last_reviewed_at    timestamptz

problem_verifications            -- 자동 검증 기록 (실행할 때마다 추가)
  id, problem_id, content_hash, layer ('L0' … 'L8'), status (pass | warn | fail),
  details jsonb (계산값, 오류 내용, 다른 해석), model (AI 단계일 때), run_url, created_at

problem_reviews                  -- 리뷰 기록 (지우거나 고치지 않음)
  id, problem_id, reviewer_id → 사용자, decision (approve | request_changes | reject | comment),
  comment text, content_hash (리뷰 당시 내용), auto_status (리뷰 당시 자동 검증 결과), created_at
```

## 5. 자동 검증 단계 (DB 기준)

| 단계 | DB에서 보는 것 | 실행 | 비용 | 결과 |
|---|---|---|---|---|
| **L0 형식** | 정답 줄(`Answer: …`)을 정답 확인 API와 같은 방식으로 해석할 수 있는지, 난이도 라벨, "It is known that"(규칙 5.9)이나 "use your answer from step"(규칙 5.4) 같은 표현, 정답 안내 문장 중복, 같은 사다리 안 정답 중복 (`problem_hierarchies`로 묶음), 카테고리 누락, 힌트에 정답 포함 (힌트 테이블이 생긴 뒤) | Python | 없음 | 실패 |
| **L1 원본 대조** (참고) | markdown 원본이 있는 사다리만: DB 정답과 markdown 정답이 같은지, 검증 스크립트가 통과하는지 | Python | 없음 | 경고 |
| **L2 독립 재계산** | DB의 문제 본문만 보고 AI가 코드를 짜서 답을 계산해 DB 정답과 비교 | Claude | API | 실패 |
| L3 AI 풀이 | 정답 없이 여러 번 풀어 일치도 확인 (AIME 수준은 AI도 자주 틀리므로 참고만) | Claude | API | 경고 |
| L4 애매함 | 다르게 읽을 수 있는 경우마다 답을 계산해 갈리는지 | Claude | API | 경고 |
| L5 규칙 | LADDER_RULES_v2, LEVEL_GUIDE 기준 평가 | Claude | API | 경고 |
| L6 원본 유사도 | `idea_cards`의 원문과 비교 (저작권, 규칙 2.4) | Claude | API | 경고 |
| L8 공개 후 관찰 | 오답이 한 값에 몰림, 정답률, 그만두는 단계 | SQL | 없음 | 리뷰 대기로 되돌림 |

- AI 단계(L2–L6)는 **미검증이거나 내용이 바뀐 문제에만** 돌립니다 (비용 관리).
- 검증은 웹 서버(Netlify)가 아니라 **GitHub Actions**(또는 로컬)에서 실행합니다. 웹 서버는 Python을 실행할 수 없고, AI가 만든 코드를 학생 요청을 처리하는 서버에서 돌리면 안 됩니다.

## 6. 리뷰 화면 (admin)

**문제 목록**
- 상태 표시: 미검증 / 자동 실패 / 리뷰 대기(승인 k/N) / 수정 요청 / 반려 / 승인 / 재검증 필요
- 필터: 상태별, "내가 아직 리뷰하지 않은 문제", 사다리별

**문제 상세 (리뷰 화면)**
1. 학생이 보는 형태 그대로의 문제와 정답·풀이
2. 자동 검증 결과: 단계별 통과·경고·실패와 근거 (예: L2가 계산한 값, L4가 찾은 다른 해석)
3. **리뷰 기록**: 시간순으로 누가, 무엇을, 어떤 코멘트로 판정했는지. 이전 내용에 대한 리뷰는 "이전 버전"으로 표시
4. **리뷰 입력**: 승인 / 수정 요청 / 반려 / 의견 + 코멘트

리뷰 저장은 서버 API를 거칩니다. 리뷰어 권한을 DB에서 확인한 뒤 기록을 추가하고, 상태와 `is_reviewed`를 다시 계산합니다.

- 검증 스크립트와 markdown은 지금처럼 만들면 되고, L1에서 DB와 대조하는 데 쓰입니다.
- 기존 파일은 고치지 않습니다. 검사기는 `scripts/verify/`에 새로 만듭니다.

**판정 철회 (Withdraw my decision)**
- 현재 내용에 대한 내 판정이 있을 때만 선택할 수 있음. 코멘트 필수, 철회 기록도 영구 보관
- 상태는 남은 리뷰어들의 판정으로 다시 계산 (예: 유일한 승인을 철회하면 리뷰 대기)
- 철회로 승인이 풀리면 학생에게 다시 숨김 (실수로 승인한 경우). 다른 리뷰어의 승인이 남아 있으면 그대로 공개
- 기존 DB에는 `problem_verification.sql` 8번 SQL(판정 종류에 `withdraw` 추가)을 한 번 실행

**수정 요청 이후 흐름**
1. 리뷰어가 **Request changes**(또는 Reject) + 코멘트
2. 상세 화면 위쪽에 열려 있는 요청 코멘트와 **이 문제에 맞는 수정 방법**이 표시됨
   - v2 사다리: markdown 수정 → 검증 스크립트 → `--update-text` (정답이 바뀌면 별도 SQL)
   - v0.1 사다리: 관리자 편집 화면 + markdown 원본도 같이 수정
   - 출처 없는 문제: 관리자 편집 화면
3. `python3 scripts/verify/report.py --save`로 재검사 → 내용이 바뀐 문제는 "리뷰 대기"로 돌아감 (이전 요청은 이전 버전 기록으로 남음)
4. 리뷰어가 다시 리뷰
- 아직 없는 것: 수정 요청 알림(이메일), 화면에서 바로 재검사하는 버튼(6단계 자동화와 함께), 수정 담당자 지정

**승인 조건**
- 현재 내용으로 자동 검사가 돌아 있어야 함. 검사 뒤 내용이 바뀌었으면 `report.py --save`를 다시 실행
- 자동 검사가 실패한 문제는 확인 체크와 코멘트가 필수
- 수정 요청·반려·의견은 코멘트 필수

**알려진 한계**
- 결정 6은 문제를 만든 사람을 알아야 하는데 `problems`에 작성자 기록이 없음. Challenge를 2명 기준으로 올리기 전에 작성자 기록을 추가해야 함
- 승인자는 `problem_reviews`에 기록. `problems.reviewer_id`는 예전 문서상 `auth.users`를 가리켜 쓰지 않음
- 예전 관리자 문제 편집 화면(`/admin/problems`)은 공개 키로 읽기 때문에, `problem_visibility.sql` 이후에는 숨겨진 문제가 목록에 나오지 않음. 모든 문제는 Reviews 화면에서 보임
- 관리자 문제 편집 화면의 사다리 연결: 목록에서 **부모가 될 문제 행을 끌어 자식 문제 행 위에 놓기**(2026-11-18 복구). Learning Path 보기에서 노드를 잇는 기능은 없어진 열(`problems.parent_problem_id`)에 쓰던 코드라 막아 둠

**문제 담당에게 생기는 변화**
- `problem_visibility.sql` 실행 이후 새로 import한 문제는 **승인할 때까지 학생에게 보이지 않음**. import 후 `report.py --save` → Reviews 화면에서 승인
- 정답을 바꾸는 수정은 `--update-text`가 거부함(기존 동작). 이번처럼 별도 SQL로 처리
