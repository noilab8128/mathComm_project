## 2. 점검에서 찾은 심각한 문제 (코드에서 고침)

### 2.1 로그인한 사용자 누구나 관리자 권한을 얻을 수 있었음

- NextAuth의 `jwt()` 콜백이 `useSession().update(data)`로 브라우저가 보낸 값을 그대로 세션 토큰에 넣었습니다. `role`도 마찬가지였습니다.
- 그래서 로그인한 사용자가 브라우저 콘솔에서 `role: "admin"`을 보내면 `/admin` 화면과 관리자 API를 쓸 수 있었습니다. 관리자 API는 토큰 안의 role만 확인했습니다.
- 관리자 API로 할 수 있는 일: 전체 사용자 목록 조회, 다른 사용자를 관리자로 지정, XP·RP 조정
- 코드 경로로 확인했고, 실제 공격은 재현하지 않았습니다.

**고친 방식**
- 세션의 role과 프로필은 항상 DB에서 읽습니다(로그인할 때, `update()`할 때, 5분마다). 브라우저가 보낸 값은 무시합니다.
- 관리자 API는 `requireAdmin()`(`src/lib/auth.ts`)으로 매번 `user_roles`를 확인합니다.

### 2.2 비용이 드는 AI API가 로그인 없이 열려 있었음

- `analyze-problem`, `generate-solution`, `generate-related-problems`는 OpenAI를 호출하는데, 세션 확인이 없었습니다. middleware는 `/api`를 검사하지 않습니다.
- 인터넷의 누구나 호출해서 OpenAI 비용을 쓸 수 있었습니다.
- 이제 관리자만 호출할 수 있습니다. admin 문제 페이지에서 쓰던 기능이라 관리자에게는 변화가 없습니다.

### 2.3 그 밖에 고친 것

| 영역 | 변경 |
|---|---|
| 로그인 실패 메시지 | "No user found" / "Incorrect password" / 소셜 계정 안내를 "Invalid email or password" 하나로 통일. 없는 이메일도 같은 시간이 걸리게 맞춤 (가입 여부 노출 방지) |
| 횟수 제한 | 모든 limiter가 기록 하나를 같이 쓰던 버그 수정. 로그인은 이메일별 15분 10회에 IP별 15분 30회 추가 |
| 이메일 | 가입·로그인 모두 소문자·공백 제거로 정규화. 대소문자만 다른 중복 계정 방지 |
| 비밀번호 | 정책을 한 곳(`src/lib/credentials.ts`)으로 통일. 72바이트 상한(bcrypt가 그 뒤를 무시함). 새 해시는 bcrypt cost 12, 예전 해시도 그대로 로그인됨 |
| 프로필 입력 | 닉네임 30자, 성별 30자, 국가 60자, 언어 30자. `is_onboarded`는 true/false만 |
| 관리자 역할 변경 | 역할 값은 "admin" / "user"만 허용 |
| 로그 | 온보딩 초기화 로그의 이메일을 사용자 id로 바꿈. 가입 오류는 오류 코드만 기록 |
| 키 | NextAuth 어댑터가 서비스 키가 없을 때 공개 키로 대신 쓰던 부분 제거 |

### 2.4 바뀐 파일

| 파일 | 내용 |
|---|---|
| `src/lib/auth.ts` | 세션 값 DB 재조회, 로그인 보호, `requireAdmin()` |
| `src/lib/credentials.ts` (새 파일) | 비밀번호 정책, 이메일 정규화, 클라이언트 IP, bcrypt cost |
| `src/lib/rate-limit.ts` | limiter별 저장소, 로그인용 limiter |
| `src/app/api/auth/register/route.ts` | 이메일 정규화, 공통 정책, 동시 가입 처리 |
| `src/app/api/user/profile/route.ts`, `reset-onboarding/route.ts` | 입력 검증, 공통 정책, 로그 |
| `src/app/api/user/stats/route.ts` | 공개 키 대신 서비스 키로 읽음 (세션 사용자 본인 데이터만) |
| `src/app/api/admin/*` (4개) | `requireAdmin()` |
| `src/app/api/analyze-problem`, `generate-solution`, `generate-related-problems` | 관리자 전용 |
| `src/app/login`, `settings`, `onboarding` 페이지 | 공통 비밀번호 정책, `update()`는 새로고침 요청으로만 사용 |
| `supabase/sql/auth_hardening.sql` (새 파일) | DB 점검 쿼리와 권한 정리 (실행 전) |

### 2.5 배포 때 영향

- 로그인한 사용자는 다시 로그인할 필요가 없습니다. 첫 요청 때 role과 프로필을 DB에서 다시 읽습니다.
- 문제 import, 아이디어 카드 업로드 등 `olympiad/` Python 스크립트는 서비스 키로 접근하므로 영향이 없습니다. SQL 2부를 실행한 뒤에도 마찬가지입니다.
- **SQL 2a(`user_roles` 공개 읽기 삭제)는 이번 코드를 배포한 뒤에 실행합니다.** 예전 코드는 role을 공개 키로 읽기 때문에, 순서가 바뀌면 관리자가 관리자 화면에 들어가지 못합니다.

## 3. 남은 문제 (DB 확인 또는 추가 작업 필요)

| 우선순위 | 문제 | 해야 할 일 |
|---|---|---|
| 1 | **관리자 문제 편집이 브라우저에서 공개(anon) 키로 `problems`·`solutions`를 쓰고 지움** (`problemsAPI`, `src/lib/supabase.ts`). 이것이 동작한다면 RLS가 anon 쓰기를 허용한다는 뜻이고, 누구나 공개 키로 문제와 정답을 고칠 수 있음 | SQL 1b로 정책 확인 → 쓰기를 `requireAdmin()` API로 옮기고 anon 쓰기 정책 제거. 문제 데이터 영역이라 **함께 진행** |
| 2 | **`user_likes`, `user_queue`, `user_starts`에 RLS가 꺼져 있음** (SQL 1c로 확인). 공개 키로 모든 사용자의 기록을 읽고, 쓰고, 지울 수 있음 | `/api/user/stats`를 서비스 키로 바꿈(코드 완료). 배포 후 SQL 2d로 RLS 켜기 |
| 3 | `next_auth` 스키마(비밀번호 해시)가 공개 키로 읽히는지 불확실. 예전 SQL이 `authenticator`에 ALL 권한을 줌 | SQL 1a 확인, 2b로 회수 |
| 4 | `solutions`를 공개 키로 읽을 수 있음 (WORKLOG 10-04~10-11 §10에서 이미 공유된 항목) | 읽기 정책 제거. 정답 확인 API는 이미 서비스 키를 씀 |
| 5 | 비밀번호 재설정 기능 없음. 로그인 화면 링크는 `#`인데 FAQ·Contact는 기능이 있다고 안내 | 기능 구현, 또는 그때까지 링크와 안내 문구 수정 |
| 6 | 가입 시 이메일 인증 없음. 남의 이메일로 가입 가능 | 이메일 인증 도입 (가입 API의 "이미 가입된 이메일" 노출도 이때 함께 해결) |
| 7 | 횟수 제한이 메모리 기반. Netlify 함수 인스턴스마다 따로 셈 | 오픈 전 Redis(Upstash 등)로 교체 |
| 8 | 비밀번호를 바꿔도 다른 기기 세션이 7일간 유지됨 | 사용자별 기준 시각을 두고 토큰 발급 시각과 비교 |
| 9 | 계정 삭제 기능, 관리자 작업 기록, CSP 헤더 없음 | 체크리스트 8.7, 5.6, 7.4 |

## 5. 함께 정할 것

1. **아동 이용자 정책.** 대상(Kangaroo, MATHCOUNTS 수준)에 초등·중학생이 많습니다. 미국 COPPA는 13세 미만, 한국 개인정보보호법은 14세 미만에 보호자 동의를 요구합니다. 나이 확인과 보호자 동의를 만들지, 이용 연령을 제한할지 정합니다.
2. **수집 항목.** 특히 gender가 학습 추천에 필요한지 정합니다. 필요 없으면 받지 않는 것이 가장 안전합니다.
3. **처리방침의 운영 주체와 연락처.**
4. **관리자 세션 유효기간.** 지금은 모든 사용자가 7일입니다. 관리자만 짧게 할지 정합니다.
5. **저장소 공개 여부.** 문제 검증 문서의 결정 1과 같은 질문입니다. 이미 push된 `Archive/docs/review_v0.3.pdf`에 아이디어 카드 출처와 정답이 들어 있습니다.
