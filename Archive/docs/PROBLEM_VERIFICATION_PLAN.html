생성 문제 검증, 어디서 어떻게 할까

작성 2026-10-14 대상 Math Quest 사다리 문제 (공개 145문제와 앞으로 만들 문제) 근거 OPERATING_POLICY, LADDER_RULES_v2, WORKLOG 10-04~10-11, review_v0.3.pdf, verify 스크립트 6개

문제는 공식 오픈 뒤에도 배치 단위로 계속 만들어집니다. 두 사람이 따로 일해도 검증은 저절로 돌아가야 하고, 사람은 마지막 승인만 해야 합니다. 이 문서는 검증 절차와 방법, 그것을 만들기 위해 필요한 것, 함께 정해야 할 것을 정리합니다.

요약

검증은 GitHub Actions에서 자동으로 실행하고, 결과는 Supabase에 쌓고, admin 페이지에서 사람이 승인합니다. 승인된 문제만 학생에게 보입니다.

GitHub Actions

검증 실행

  • 문제 파일이 push되면 자동 실행
  • Python 검사(형식, 검증 스크립트, 정답 대조)
  • Claude를 headless로 실행하는 AI 검사
  • 통과하면 숨김 상태로 import
Supabase

결과 보관

  • 문제별, 단계별 검증 결과와 근거
  • 어느 커밋, 어느 실행에서 나온 결과인지
  • 공개 후 오답 분포 집계
src/app/admin/problems

사람 승인

  • 검토 대기열에서 결과를 보고 승인 또는 반려
  • "증명 의존" 문제는 증명을 읽고 판단
  • 다시 검증 버튼

웹 서버(Netlify)에서는 검증을 돌리지 않습니다. Netlify Functions는 JavaScript, TypeScript, Go만 지원해서 Python 스크립트를 실행할 수 없고, 무거운 계산이나 AI가 만든 코드를 학생 요청을 처리하는 서버에서 실행하면 안 됩니다. Supabase Edge Functions도 TypeScript 전용입니다.

트리거

  • 문제 파일 PR/push (olympiad/ladders/**): 주 트리거. 문제 담당자는 지금처럼 markdown을 쓰고 push만 합니다.
  • 매일 밤: "대기" 상태 문제를 다시 확인하고 L8을 집계합니다.
  • admin의 다시 검증 버튼: GitHub API(workflow_dispatch)로 같은 workflow를 실행합니다.

AI 검사의 자동 실행

  • Claude Code 스킬은 세션 안에서만 돌기 때문에, Actions에서 Claude Code를 headless로 실행합니다(claude -p 또는 공식 GitHub Action).
  • 스킬과 프롬프트는 저장소의 .claude/skills/에 둡니다. 로컬에서 수동으로 돌릴 때와 CI에서 같은 스킬을 씁니다.
  • AI가 만든 코드는 실행할 때마다 새로 뜨는 Actions 가상 머신 안에서만 실행됩니다.

공유 사항

검증과 함께 알아야 할 것

Challenge가 승인 대기열에 나오지 않음

import 스크립트는 단계에 is_generated = true, Challenge에 false를 넣습니다(import_ladders_v2.py 137행). admin의 "Pending AI Review" 필터와 승인 버튼은 is_generated = true인 문제에만 나오므로, Challenge 28개는 지금 승인 화면에 나타나지 않습니다. Challenge도 생성한 문제이므로 플래그 의미를 다시 정해야 합니다.

숨김만으로는 정답이 보호되지 않음

solutions 테이블은 공개 키로 읽을 수 있습니다(WORKLOG §10). 승인 전 문제를 화면에서 숨겨도 정답은 그대로 읽힙니다. 숨김 처리와 solutions 읽기 정책 수정을 같이 해야 합니다.

공개 저장소와 Actions 로그

공개 저장소에서는 Actions 로그를 누구나 봅니다. 검증 로그에는 정답과 출처가 찍힙니다. 이미 커밋된 LADDERS_v2_batch*.md와 v0.x 초안에도 정답과 Idea card: SL… 줄이 들어 있어서, 출처를 내부용으로 둔다는 OPERATING_POLICY 2.4와 맞지 않습니다.

검증 범위

  • 먼저: 이미 공개된 145문제. v2 P1–P21(108문제)과 v0.1 사다리 7개(37문제)가 모두 is_reviewed = false 상태로 학생에게 보이고 있습니다.
  • v0.1: 단계가 풀이 경로에서 벗어난 곳과, 1단계가 v2 기준보다 낮은 문제가 있습니다(WORKLOG §11-3). 검증 결과로 교체 여부를 정할 수 있습니다.
  • 파이프라인 밖: 증명 문제(16 + 21)는 숫자 답이 없어 L1–L4가 맞지 않습니다. 사람이 읽는 별도 목록으로 관리합니다. Theory 카드 링크도 주기적으로 확인합니다.
  • 나중에: 초안 G/H(v0.2), I–AB(v0.3)는 v2로 다시 만들 때 같은 절차를 거칩니다.

채점기와의 관계

풀이 제출 채점(/api/grade-solution)은 저장된 정답을 쓰지 않고 AI가 직접 풀어 판단합니다. 그래서 어려운 Challenge는 잘못 채점될 수 있습니다(OPERATING_POLICY 3). 검증을 통과한 정답을 채점에도 쓰게 하면 이 한계가 줄어듭니다.

결정

함께 정할 것

1. 저장소 공개 여부

Actions 로그와 커밋된 문제 파일에 정답과 출처가 남습니다.

저장소를 비공개로 전환 (추천)공개 유지, 문제 파일만 별도 비공개 저장소로

2. 승인 전 문제의 공개 여부

자동 검증이 학생을 보호하려면 승인 전 문제가 보이지 않아야 합니다.

승인 전 숨김, 공개된 145문제는 일괄 검증 뒤 승인 (추천)"Beta" 표시 후 공개

3. 차단과 경고의 기준

L0, L1, L2 실패는 차단, L3–L6은 경고 (추천)L3도 차단

4. AI 검증 비용 한도

배치마다 L2–L6에 API 비용이 듭니다. L3 샘플 수와 월 한도를 정합니다.

5. 승인 권한
